## Reproduce isolated verification

Use Node 22 LTS and locked dependencies. CI uses the latest available Node 22 patch through setup-node; the local evidence records the actual installed version, 22.12.0. Install with npm ci --ignore-scripts --no-audit --no-fund. Run npm run check:f00 in either repository. The app runs isolation controls, its tests, typechecking and a web build with envDir false into .f00-evidence/web. The bot builds and runs its existing serial tests plus the shared producer fixtures; without --postgres it uses in-process PGlite and explicitly reports PostgreSQL-only skips.

For real PostgreSQL checks use a disposable loopback instance, database mentorship_test or htnq_f00_<suffix>, and the synthetic test:test role, then npm run check:f00 -- --postgres with an explicit TEST_DATABASE_URL. The runner refuses non-loopback hosts, non-test credentials/databases, query options or missing URLs. CI already provisions a fresh PostgreSQL 17 service and now runs this required profile; it cannot quietly substitute the PGlite profile. No paid/test cloud instance is provisioned.

The runner allowlists only OS/path/temp settings, replaces the application database/token with unusable synthetic values, drops all inherited provider credentials and node injection, disables dotenv via the tracked empty.env and preloads a Node network guard. The guard permits loopback mocks and rejects external fetch/socket connections. A positive loopback test and negative external-socket/fetch tests verify both sides. These are regression controls for trusted project tests, not a security sandbox for hostile code or permission to start a worker against live services. No recipients are approved for external test delivery; the tests use in-memory adapters and loopback HTTP, never real Discord/Stripe/email/Supabase/Bunny.

Full logs and per-stage exit codes are saved under ignored .f00-evidence/. CI uploads those synthetic-only reports for seven days. Do not copy an operator .env into CI/artifacts. F00 does not invoke npm start, dev, migrate, register, release, deployment CLIs or the member-access administrator against production. Production-source files and existing migration checksums remain unchanged.

On the app, node scripts/f00/check-paired.mjs <bot-checkout> compares byte-identical shared register/fixtures and calls the actual app client against the actual bot HTTP handler with synthetic records over loopback. This checks nine decisions, wrong-token rejection, strict response/denial privacy and redacted logging. It is a real local producer/consumer check, not a deployed-cloud, Discord-login, browser-playback or paid-payment test.

## Delivery changes and approval

The app verification workflow now checks PRs and main pushes and is reusable through workflow_call. The Pages workflow reuses the same verification as a required preceding job, restricts publication to main and uses Node 22 consistently. A failing verification prevents that run's build/deployment; a passing branch check is not owner approval to merge. Node 20 is EOL in the current official release table, while Node 22 is LTS: https://nodejs.org/en/about/previous-releases. Local reusable workflows run from the caller's same revision: https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows. Existing GitHub Pages target/configuration is retained; there is no Vercel cutover.

The bot preserves its existing PostgreSQL/preview/audit/Docker CI checks and uses the isolated runner for build/tests. No deployment step is introduced. Required GitHub branch-check/ruleset configuration must be confirmed through the actual repository settings; source YAML alone does not prove merge protection. No branch-protection or environment setting was modified by F00.

Use docs/contracts/register.md and release-manifest.example.json. Before owner approval, fill the actual candidate heads/PRs, CI results, target identities, auto-deploy effects, compatibility and rollback. No new schema, Edge Function, desktop runtime or payment contract is deployed in F00. App and bot v1 runtime source remains unchanged, so there is no API activation/migration order dependency; still review both candidate commits as one logical feature. Existing HTTP contract/payment/role thresholds, finite tuition, Stripe pin and signed records are preserved.

After the combined approval, merge the exact validated candidates in dependency order and confirm accepted main checks. App main automatically triggers its existing Pages publication, now behind verification. Bot main may trigger its existing external auto-deploy configuration; confirm that target in the approval manifest first. There is no second hidden approval ceremony. If a candidate changes or a conflict is resolved, recheck the actual merge candidate. No plan guarantees future branches never conflict.

For rollback, revert only the named feature commits through normal review/verification and redeploy the previous known-good affected target under the applicable approval. Do not force-reset shared main, rewrite immutable migrations, restore production data for a CI/docs issue or recreate a merchant. Record observed revisions after release; a green installer or static test is not whole-platform production verification.
